## Engineering Doctrine

### Reality Over Rhetoric

Claims should be supported by working artifacts, tests, deployment evidence, maintenance history, or measurable outcomes.

### Architecture Before Implementation

Before building, define the objective, system boundary, source of truth, trust boundaries, acceptance criteria, and smallest durable implementation.

### Local Control by Default

Prefer systems that preserve user ownership, remain useful offline, expose stored data, and avoid unnecessary accounts or cloud dependencies.

### Reversibility Over Cleverness

Consequential operations should include validation, backups, visible failure handling, recovery instructions, and rollback paths.

### Dependencies Must Earn Their Place

Libraries and services are useful when their value exceeds their supply-chain, size, maintenance, privacy, and offline costs.

### Chat Is a Workbench, Not a Database

Important decisions, state, artifacts, and verification results should be promoted into durable project records.

### Verification Defines Completion

A successful first run is not enough. Serious deliverables should include proportionate testing, documentation, security review, accessibility review, packaging, and recovery procedures.

## Build Lifecycle

My preferred build loop is:

1. Define the real objective.
2. Establish the system boundary.
3. classify sources and trust levels.
4. Select the execution environment.
5. Define security and privacy boundaries.
6. Establish the canonical source of truth.
7. Build the smallest durable vertical slice.
8. Add logging and visible failure handling.
9. Run functional and negative tests.
10. Package artifacts with version and integrity metadata.
11. Validate the workflow under real conditions.
12. Ship, monetize, merge, pause, kill, or archive deliberately.
13. Document the recovery and rebuild path.
